## Authenticated workflow

The actual Company application now exposes `/custody` in Financial Operations for Accounting Admin, Accountant and Management Viewer. It uses authenticated Supabase only, never demo/local business data. Existing Parties provide primary Custodians and secondary Employee/Custodian roles; no person is represented as a Treasury. Select a holder, refresh the authoritative register/balance, enter a supported business transaction, review its frozen inputs, confirm and retain the canonical receipt. All recorded dates are explicit; no historical opening or production data is invented.

- Funding/replenishment: existing `post_custody_advance`, real active Treasury, optional non-closed Project, positive exact amount and actual original external reference/evidence. Project-linked Treasury selection respects its Project. Transfers debit the person-scoped custody receivable and credit Treasury; no expense/VAT/cost is recognized.
- Custody-funded Expense: existing `post_expense` with CUSTODIAN funding, explicit holder/category/Project or overhead, net/VAT/invoice/method/description and source evidence. Input validation reuses the established Expense contract; review shows exact gross/VAT using canonical positive half-up rounding. The server remains accounting authority and checks funded pooled balance. There is no arbitrary GL or journal-line input. The original external source reference is preserved in Expense notes because the existing Expense command has no external-reference parameter.
- Returns: existing `post_custody_cash_return`, independent of settlement, to a valid Treasury. No Project is inferred. It debits Treasury and credits custody without changing cost. Inactive holder history/returns remain supported by existing commands.
- Settlement: existing `finalize_custody_settlement`, 1–999 selected posted, same-holder custody Expenses, expected exact gross sum and notes. Existing immutable item uniqueness prevents a second grouping of an Expense. This creates no journal and never recognizes cost again. The register explicitly marks included/unsettled Expenses; there is no settlement cancellation command.
- Corrections: Accounting Admin alone can select existing posted funding/return/Expense documents for the appropriate `reverse_custody_advance`, `reverse_custody_cash_return` or `reverse_expense`, with reviewed date/reason. Server dependency/period/Project guards remain authoritative. No posted financial history is edited and no corrected replacement is posted automatically. The canonical Expense reversal currently permits an already-grouped Expense to reverse while preserving its original immutable settlement membership; the register shows current REVERSED status and original grouping separately.

Managers see balances/history/reports and no posting or reversal forms. Existing server permission checks, Company membership, RLS, source uniqueness, locks and commercial readiness still enforce the database boundary. New funding/Expense presentation requires FULL confirmed commercial access; permitted existing settlements/returns/reversals remain independently available. The new UI does not grant any new role permissions.

## Exact requests and uncertain outcomes

Every monetary input becomes an exact minor-unit decimal string; no floating-point financial amount is persisted. Existing keyed financial commands retain a frozen UUID/payload. A user/Company-scoped sessionStorage envelope contains only the command intent and canonical receipt, not a balance, Auth token or alternate ledger. Production-boundary validation explicitly allows only this additional recovery form, following existing financial-form conventions.

Persisting the request must succeed before dispatch. Double clicks/remounts in the tab share one in-flight request; different intent cannot replace it. Session/generation changes before dispatch stop submission. A response lost after commit freezes inputs, survives reload and retries the same key. Only a definite rollback on the first transmission permits editing with a new key. Confirmed posting with failed readback remains visibly confirmed and must refresh, not repost. Storage corruption disables entry while independent database-backed reporting remains available.

Settlement has **no canonical idempotency-key argument**. It is not passed a fictional one. Before dispatch and after a returned error, recovery reads immutable item/header records: exact Expense set (including no extra items), Company, holder, actor, date, notes, finalized state and expected total must match. A matching existing group returns its receipt without another finalization. Lost/malformed responses retain the request; a subsequent retry recovers the group. Competing selections serialize on the existing holder/Expense locks and unique Expense membership; a partial/different group is a retained conflict for accounting review, never silently accepted or deleted. This is uniqueness-based recovery, not a claim that the legacy command gained keyed replay or cancellation.

## Cash gate and precise deferred contracts

**Cash-funded issuance and reversal of a return into a CASH Treasury are disabled in this new UI.** The existing commands do not establish verified physical-cash/opening completeness or a transaction-safe Treasury cash-sufficiency check. A browser balance check would not establish that control under competing withdrawals, so none is presented as a database guarantee. Bank-funded issuance, custody Expenses, cash/bank returns, bank-return reversal and eligible funding/Expense reversals are supported. Existing direct canonical command permissions/behavior are unchanged; this is a bounded UI gate, not new global cash enforcement. Full cash-out requires its separately reviewed source/opening evidence and canonical sufficiency/concurrency contract, with shared-production recovery/activation gates before any migration.

Personal-funds spending/reimbursements remain separate and unavailable for posting here. Missing contracts are: evidenced personal-payer recognition and approval; configured stable person-scoped reimbursement liability account and valid VAT/Project dimensions; source matching that avoids recognizing an existing Expense twice; bounded partial/full reimbursement payments and Treasury sufficiency; and exact reversal/dependency/idempotency rules. CUSTODIAN mode may not be used beyond its funded pool, and neither a signed CUS-03 difference nor personal evidence automatically creates a liability. Owner/partner funding/drawings are not substituted for employee reimbursements.

Also deferred: physical counts/variance and bank reconciliation, certified opening balances, historical import execution, secure attachment uploads, an auditable unposted personal-evidence/submission store, explicit many-to-many holder/Project master assignments and settlement cancellation. Existing Project dimensions already support different holders and multiple Projects without partitioning the pooled receivable. The August2026 template remains evidence collection only. No Maker/Barq identifiers or assumptions are introduced. Wider M3/CON requirements remain incomplete.
