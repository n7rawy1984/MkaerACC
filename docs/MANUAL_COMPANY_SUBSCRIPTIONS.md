## Existing architecture and scope

The existing Platform Owner foundation held `plan_key` metadata (`UNASSIGNED`, `TRIAL`, `STANDARD`) in `private.platform_entities`; its Subscriptions page was a placeholder. Company lifecycle, active membership, financial permissions and RLS already enforce Company access independently. This change reuses those controls, owner registry/live-session/fresh TOTP validation, request receipts/recovery and immutable `private.platform_events` audit. It adds one current service subscription per Company, not accounting books or gateway billing.

## Implemented behavior

- Owner → Subscriptions → Manage / renew subscription: select Company, Trial or Standard plan, recorded Trial/Active/Expired/Cancelled state, inclusive start/end dates, manual billing method, payment status/reference and mandatory audit reason. The existing MFA and explicit reconfirmation flow protects writes and uncertain-response recovery.
- Trial requires Trial plan; Active requires Standard. Billing methods: None, manual cash, bank transfer or other. Payment statuses: Not required, Unpaid, Paid or Waived. Paid requires a non-None method and reference. These are operator assertions, **not receipts proving money movement or accounting postings**. Unpaid does not independently disable access; the owner explicitly sets the service state/period. No automatic charging or renewal.
- Dates are calendar dates in `Asia/Dubai`; end date is inclusive and renewal is due the following day. Automatic effective expiry is evaluated on each database operation/read, with no scheduler. A future start displays Not started (`SCHEDULED`, derived only); Cancelled takes precedence. The workspace refreshes display on focus and every minute; database enforcement uses current server time regardless of stale UI.
- Existing Companies begin `UNMANAGED` with existing access retained. **No backfill or automatic trial assignment.** New commercial onboarding must explicitly assign a subscription; Company activation/accounting provisioning alone does not enroll one. The directory and workspace display this state. This compatibility policy preserves the 17 historical Companies; blanket lockout is not part of this migration.
- A primary key on Company, Company/row locks, expected subscription version and normalized request hash prevent overlapping current subscriptions, lost updates and duplicate effects. Version zero means not yet enrolled. Renewal updates the same current record; before/after state and reason remain in immutable audit. Same-key/same-intent recovery returns the existing receipt; changed intent is rejected. Concurrent different-intent enrollment cannot create two current rows: commands serialize on the existing owner authorization lock and Company row, then validate version.
- The existing entity editor no longer assigns plans. A database trigger prevents its old RPC from contradicting an enrolled subscription. Existing directory metadata is synchronized without adopting or modifying historical financial data.
- Member status reads require existing active Company membership; owner authority does not bypass financial RLS. Private subscription data has forced RLS and no client table grants. Members see status/dates/plan/payment status, not owner identity or manual payment reference. Existing Company status and membership remain authoritative and unchanged.

## Expired, cancelled and not-started access policy

These states are **limited access, not suspension**. Company members keep existing role-scoped reads/reports, master maintenance, settlement of existing obligations/receivables and valid reversals. This preserves accounting history and avoids trapping existing liabilities. The owner console remains accessible under independent owner authority. Company suspension remains a separate action with its existing semantics.

Database INSERT guards reject new projects, parties/person roles, categories, GL accounts, Treasury, subcontracts, expenses, custody/subcontractor advances, certificates, payroll postings and historical source records. They also reject creation of attendance/payroll period headers. INSERT/UPDATE/DELETE guards restrict payroll draft detail/adjustment/accounting rows, attendance exceptions and employee site assignments. Existing period-header updates deliberately remain available because payroll reversal must unlock attendance and invalidate review. Draft header review alone cannot post payroll; the posting insert remains guarded.

Existing supplier/subcontractor/retention/salary payment and reversal paths, custody settlement/cash-return paths, journal corrections and existing-master updates retain their existing checks. No subscription check grants any additional financial permission. No journal, amount, posted document or membership is changed merely by expiry or a subscription update. Existing financial commands enforce all their original dimensions, balances and reversal dependencies. The Company lock precedes the subscription lock to serialize initial enrollment with guarded business creation.
