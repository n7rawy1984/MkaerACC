## Existing architecture and the missing integration

- Company creation is `platform_admin_command('create_entity',...)`: empty INACTIVE Company, Company settings, DRAFT entity metadata and optional administrator membership. Activation is a separate lifecycle command requiring an active Accounting Admin. Activation grants access; it does not create books.
- Existing P3 `accounts` is the authoritative GL. Unique indexes enforce normalized Company/code and Company/system-key identity. Accounts are scoped by existing RLS; browser changes remain name-only. Protected operator tooling in `scripts/admin/provision-gl-accounts.mjs` already defines ten supported system-key/type meanings; its existing behavior is unchanged.
- Existing Treasury is a real money location permanently linked one-to-one to a same-Company ordinary Asset GL account. Existing Treasury creation/status commands, constraints and mapping triggers remain intact. Parties, expense categories, Projects and Subcontracts are operation-specific masters.
- The journal kernel and specialized commands enforce `BIGINT` amounts, stable-key resolution, dimensions, balanced immutable journals and business-command idempotency. No new posting engine or generic journal endpoint is introduced.
- The current product formats AED. Calendar-year numbering is allocated lazily by `private.reference_counters(company_id,reference_type,fiscal_year)` from transaction dates. There is **no existing configurable fiscal calendar, fiscal-period provisioning table or period-closing setup flow** to seed. Company settings hold locale/branding, not currency or fiscal accounting policies. This implementation preserves those behaviors and creates no artificial fiscal periods/counters or tax facts.
- The confirmed gap: `private.platform_entities.accounting_setup` previously allowed only INCOMPLETE, and new Companies had no GL accounts. No supported transition connected activation to a usable accounting foundation.

## Implemented workflow

New forward-only migration: `supabase/migrations/20261101120000_company_accounting_provisioning.sql`. Existing62 migrations are unchanged.

1. **Created:** DRAFT/INACTIVE Company, pending or assigned administrator. No automatic provisioning.
2. **Activated:** existing lifecycle command makes Company ACTIVE. Accounting remains INCOMPLETE; the workspace explicitly reports setup pending.
3. **Provision:** Platform Owner selects **Provision accounting** on the exact ACTIVE/INCOMPLETE entity, reviews its name/code and supplies the actual primary Treasury location name, Cash/Bank type, bank name for Bank only, and an audit reason. Existing explicit confirmation, fresh MFA and request-recovery UI apply. The server independently checks all authority and identity values.
4. **Complete:** one transaction inserts11 GL accounts, one zero-balance Treasury master, private provisioning evidence, an immutable platform audit event and a confirmed request receipt; then marks setup COMPLETE and increments entity version once. The directory and recipient workspace distinguish this from activation.

The baseline template is `CONTRACTING_BASELINE_V1`:

Treasury code PRIMARY is linked permanently to the ordinary Asset GL. The location name/type are explicit owner business inputs, not inferred cash/bank existence. No cash balance, opening entry, capital, revenue recognition, tax registration/rate, Party, Project, Subcontract, reference sequence row or financial transaction is created by provisioning.

**COMPLETE means this baseline foundation was provisioned, not that every business operation or commercial onboarding requirement is complete.** Actual supplier/category/Project/contract masters, legitimate funding and transaction inputs still belong to their existing authorized flows. For example, supplier-credit expenses require an active Supplier and category but no invented opening cash. Treasury-funded operations need actual funds and their operation-specific prerequisites. COMPLETE is durable setup history, not a guarantee that every master remains active forever; later normal Treasury status/name changes are not silently undone by retries.

**DECISION REQUIRED for future owner-funded operations:** the approved GL infrastructure deliberately excludes OWNER_CURRENT because its frozen account-type treatment is not established (`docs/GL_SYSTEM_ACCOUNT_PROVISIONING.md`). This implementation preserves that exclusion. It does not invent an Equity/Asset/Liability mapping to make owner-funded expenses work. Owner-funding support is not included in this baseline's completion claim. No ambiguity affects the ten existing supported mappings.

## Authorization, preservation and retries

`public.provision_company_accounting(request_id,business_input)` is a narrowly scoped SECURITY DEFINER function with empty search_path. Only authenticated may execute; actual authorization calls existing `private.platform_actor()` under the existing authorization lock: active registered owner/profile, genuine live session, AAL2 and fresh verified TOTP. Ordinary Accounting Admin, Accountant, Viewer, foreign user and Company SYSTEM_ADMIN cannot provision; service_role/anon have no EXECUTE grant. The caller cannot supply arbitrary accounts, system keys, GL IDs, journal lines, amounts, actor IDs or completion status. This is fixed new-Company master provisioning, not cross-tenant financial read/post authority.

The exact UUID/code and ACTIVE Company/lifecycle are checked and locked FOR UPDATE, with active Accounting Admin required. Initial setup also requires the original platform `create_entity` audit event, current entity version and INCOMPLETE status. Every public Company-owned business table must be empty except existing Company settings/memberships, and no private reference counters may exist. This rejects legacy/adopted Companies, partial charts and existing business data instead of taking over or remapping accounts. It never updates an existing account or Treasury. No Company is backfilled when the migration is applied.

`private.company_accounting_provisions` records the unique Company/template, normalized intent hash, generated account/Treasury IDs, actual actor, request and timestamp. It has forced RLS and no browser/service-role table grants. Existing immutable `platform_events` records the reason/template/count/Treasury reference. Existing `platform_requests` supplies normalized request hashing and durable receipts. A mismatched request UUID payload fails. Equivalent new request UUIDs reuse the foundation and get a receipt without duplicating financial masters or incrementing entity version. Different Treasury intent fails; there is no automatic repair/takeover. Receipt recovery still rechecks owner authority and ACTIVE Company access. Late failures roll back all inserts, metadata, receipt and audit together.

Company-row serialization and the unique Company provisioning PK protect competing initialization; existing account/Treasury unique indexes remain a second boundary. A subsequently approved genuine two-connection race test passed6/6 on disposable native PostgreSQL18.4, including observed backend lock waits, concurrent retries, rollback and lifecycle/version fencing. [Exact race evidence and cleanup](COMPANY_ACCOUNTING_PROVISIONING_RACES.md). The earlier55-check embedded suite remains distinct from this native concurrency evidence.

`public.get_company_accounting_setup(company_id)` permits only an active member of that exact Company and returns only Company ID/setup status. Platform authority alone cannot read the Company's chart or use this member-only status RPC. Existing unclassified/adopted legacy Companies return UNASSESSED and receive no setup classification or new block. Workspace status is read-only, remounted for identity/Company changes and never provisions on load, refresh or sign-in. Failed reads show unverified status rather than success.
