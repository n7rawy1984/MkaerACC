# CON-03 / CON-05 — Business Party master and lifecycle

Implemented 2026-11-04 for the existing Company-owned SUPPLIER and SUBCONTRACTOR records in production `/parties`. This is the business-party metadata/lifecycle increment, not completion of every CON/M3 requirement. Existing Party UUIDs, primary types and contract/financial references remain authoritative. Maker has no special branch. Employee, Custodian, Owner and Other identity controls are preserved.

Existing core creation forms remain available, with a visible normalized name/TRN duplicate warning and explicit acknowledgment before deliberately creating a separate visible identity. Full business metadata is maintained through the same record's detail/edit control: display/code, optional legal name, business classification, trade-license number/authority/expiry, TRN, contact person/phone/email/address, two-letter country code, emirate/region, payment-terms reference and internal notes. No license, TRN, country or terms field is mandatory. Party primary type remains immutable; business classification does not convert identity or subledgers. Payment terms are master reference text and never overwrite contracts, due dates or financial calculations.

Country is not assumed to be UAE. Foreign tax identifiers remain text. Explicit AE records with an optional TRN receive a 15-digit format check; this does not verify registration or change invoice/VAT rules. The [UAE Ministry of Finance mandatory-fields document](https://mof.gov.ae/wp-content/uploads/2026/02/UAE-Electronic-Invoice-mandatory-fields_V-1.0-23Feb2026.pdf) describes the 15-digit TRN. Actual registration verification remains an operator task through the [FTA verification service](https://www.tax.gov.ae/en/statuscheck.aspx). Expired licenses remain saved and visibly flagged for review; no invented automatic prohibition or historical backfill is introduced.

The controlled workflow loads current details/history, prepares an exact-version preview, records an optional metadata reason or required status reason, shows changed fields/status, then explicitly confirms. Deactivate/reactivate keeps identity, history and balances. Normalized same-Company name/legal name/TRN or license+authority+country matches require acknowledgment during controlled edits, never automatic merging. Existing cross-type code uniqueness remains authoritative. Creation warnings use visible current masters and are advisory, not a new uniqueness guarantee. Concurrent independent creation may still need operator duplicate review.

## Database and authority

Forward migration `20261104140000_party_business_master_lifecycle.sql` adds eight nullable Party fields, immutable forced-RLS business-change and request tables, private validation/authority/audit helpers and two authenticated-only preview/update RPCs. All existing function definitions, role maps, Party SELECT policies, financial commands and original RLS are preserved. Management reuses active ACCOUNTING_ADMIN/PROCUREMENT plus `party.manage`; another Company, Accountant, Viewer, Data Entry or SYSTEM_ADMIN cannot invoke the new writer. New fields have no browser DML grants. Sensitive Employee/Owner rows are outside this business command and duplicate search. Audit/report reads inherit the existing Party row visibility; no public contact/registration endpoint is added.

The database derives the actor; locks Company/profile/membership and the exact Party version; hashes normalized fields, expected version, actor, reason/status and duplicate acknowledgment; serializes request keys; commits master, immutable before/after event and replay receipt atomically. Changed-intent replay and stale versions fail. Same-key replay returns the original receipt even after the master advances. New lifecycle transitions require a reason through the controlled command; direct browser status changes are denied. Legacy metadata-only edits/creation remain compatible and are automatically audited. Older/trusted events without a command reason are shown as unrecorded, never assigned a fabricated reason. There is no audit backfill for existing records. Business identities and immutable evidence cannot be deleted through this implementation.

A confirmed native concurrency test found the existing Supplier Expense engine checked status before its FK wait. A narrow new BEFORE INSERT trigger now locks/rechecks the same-Company Supplier before new Expense recognition. It changes no amount, VAT, posting/reversal function or previously posted row. New Subcontracts already lock/require an active Subcontractor; new advances retain their established active-party controls. Certificates on existing contracts retain their existing recognition policy; inactivity is not a new automatic bar on recognizing already incurred contractual liabilities.

Existing Supplier/Subcontractor payments and retention release/payment remain available for legitimate existing obligations after inactivity. No contract amount, retention rate, VAT treatment, posted journal or historical transaction changes when metadata/status changes. Existing IDs supply consistent Party labels throughout contracts and accounting. No accounting entry is generated by master maintenance.
