# Private Document Management V1

Implementation baseline: deployed `31efd93418b2b3e42de9f90962ffa6a326369085` (Product Owner confirmation), hosted migrations through108. This phase adds evidence management only; no accounting command or historical transaction is rewritten. The isolated release contains Migration109, not a hosted activation.

## Workflow and associations

Open an existing record's details → **Private documents / الوثائق الخاصة** → attach → preview/download. Multiple documents per record are supported. Existing canonical IDs identify Expenses (including Supplier invoices), Customer invoices, Purchase Orders, Requisitions, RFQs/received Supplier quotations, Goods Receipts, receipt-first invoice drafts, Projects, construction contracts, subcontracts, contractor certificates, Treasury/Custody posted journal movements, journal-free Custody settlements and Employee records. Supplier AP and Expense details share the same Expense identity. Receipt-first invoice attachments are also visible from the resulting canonical Supplier invoice; neither source nor financial document is rewritten.

No new general document route, accounting engine, approval layer, Party record or financial posting is introduced. Unsaved transactions must first have an existing canonical ID. RFQ quotations share their parent RFQ and use their display titles/original filenames to identify the quote. Treasury/Custody money-movement evidence uses the canonical posted journal ID, not a fictitious payment. Custody settlements retain their own canonical settlement ID and existing confidential full-Custody access restriction; no journal is fabricated for a settlement.

The panel supports title editing, original filename preservation, upload status/retry, version history, actor/reason audit, and association removal where permitted. Replacement adds a new version and retains every earlier file. Original file bytes, path and evidence stay available. No browser physical-delete or overwrite API exists. Removed associations remain visible as historical records, with their files retained. Posted/issued evidence cannot be detached; additions, audited title corrections and append-only versions remain possible. Construction agreements/subcontracts are retained conservatively from creation. No journal, VAT, period, account, stock, payroll or payment calculation is modified.

## Security and database boundary

Migration109 creates three Company-owned metadata tables with forced RLS and SELECT-only browser grants, five constrained functions, an immutable audit trigger, one private Storage bucket and six bucket-specific policies. Existing functions, grants, accounting tables and policies are not altered. Private helper access is revoked from browser roles. Public boolean access checks expose no content or metadata without live membership and target authorization. All definer functions use a fixed empty search path.

The database resolves targets using an explicit entity allowlist, active Company membership, existing roles/project assignment, confidential HR permission and existing payroll/construction/annual-journal visibility. Platform administration is not a Company financial bypass. Management Viewer can read allowed ordinary files only; Procurement is limited to existing Project and purchasing access. Employee files require existing `payroll.manage`. Files can also be explicitly marked confidential within other workflows, with the same restriction across RPC, metadata RLS, history and Storage. Confidentiality and entity identity cannot be downgraded or reassigned after creation. Users must select the confidential option for personnel/payroll material outside dedicated Employee/journal flows; the system does not infer content using AI.

Storage paths are generated by the database: `<company UUID>/<document UUID>/<file UUID>.<allowed extension>`. Upload requires a live, actor-owned reservation (24-hour upload window). The bucket enforces a10MB limit and allowed MIME types. The client additionally validates extension, basic file signatures, size and safe filenames before reservation. Completion verifies the actual Storage object's owner, byte size and MIME metadata. SHA256 is a client-calculated recovery fingerprint, not a server antivirus/content authenticity attestation. HTML, SVG, executable and macro-enabled extensions are excluded. Office files and text download; PDF inline previews are sandboxed and include an isolated native-browser viewer link when a browser blocks embedded PDFs; images render as images.

Restrictive SELECT/INSERT/UPDATE/DELETE policies protect this bucket even if unrelated permissive Storage policies exist. They do not broaden access to other buckets. Object overwrite and physical deletion are blocked for browser roles. The migration stops if its named bucket already exists rather than silently changing an existing bucket. Other buckets are untouched.

Reads/downloads request a120-second Supabase signed URL only after live authorization. The application checks its origin/path, fetches without caching/credentials/redirects, rechecks access and previews/downloads a temporary Blob. URLs are never persisted in database or session storage. Blob URLs are revoked on close/unmount/session change; existing bearer grants can remain valid until their120-second expiry. As with any authorized download, a copy already downloaded cannot be revoked. Browser clients with direct Storage API access can request a different signed TTL where Supabase permits; the120-second limit is the application policy, not a claim of a service-side maximum. All generated production UI links use120 seconds.

Requests bind actor, Company, action and normalized JSON under unique idempotency keys. Existing Company operational locks plus row locks/expected revisions serialize changes. A partial unique index permits one pending upload per document. Reservation and completion retries reuse stable request IDs. An explicit Recover saved upload action detects an already-completed file without uploading it again, or finishes an uploaded-but-uncompleted reservation. Recovery metadata is scoped by user/Company/entity and cleared on sign-out; file bytes/URLs/credentials are never persisted there. A committed upload whose response is lost can be recovered with the same file; completion is idempotent. A pending upload can be explicitly abandoned by its original uploader. Earlier ready versions remain accessible during failed replacements.

## Verification and operational limits

Exact executed checks and evidence are in `private-documents-verification.json` and `private-documents-evidence/`. Local test scaffolds emulate Supabase Auth and Storage HTTP/catalog behavior while running actual canonical SQL, RLS and browser components. They are not hosted Storage service or genuine production authentication acceptance. A focused real service upload/sign/download/expiry smoke remains required after explicit109 activation and compatible publication, in an authorized fictional environment. No Maker or other real-company data was changed.

No antivirus service, OCR, full-text search, Office inline rendering, public sharing, automatic retention cleanup, orphan garbage collection or historical file import is added. Abandoned/stale uploaded objects are retained without destructive cleanup. A reservation older than24 hours must be abandoned and a new version reserved; only the original uploader can complete/abandon it in V1. Physical evidence disposal/retention automation and access-log retention policies remain operational work. There is no silent fallback to demo/local storage.
