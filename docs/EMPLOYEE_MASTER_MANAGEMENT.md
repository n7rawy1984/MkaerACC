2026-11-06. Implemented locally; migration84 NOT APPLIED; frontend NOT PUSHED/DEPLOYED. This is an Employee-master operational increment, not full statutory HR/WPS completion.

## Existing foundations reused

Employee identity remains the Company Party and its EMPLOYEE person role (including Employee/Custodian dual roles). Registration delegates to existing `create_person_party`. Effective employment versions, exact-money compensation and default Project remain `command_hr` / `hr_term_events`; policy, attendance calendar/minutes, payroll profile/accrual/payment/reversal and employee receivables remain the existing HR/Payroll commands. No Employee table, payroll calculation engine, ledger or legal deduction policy is added. An optional default Project is configured through the existing employment/payroll profile or Attendance site assignment, never through a GL account.

Previously registration was tucked into Parties, payroll profiles into Payroll, and employment terms into the large Attendance/Payroll workspace. Employee metadata editing was name-only, the dashboard card was marked under development and there was no Employee sidebar entry. These are the gaps addressed.

## Operator workflow

- Open Employees under Employees & Payroll or the dashboard Employee card, which now links to `/employees`. Existing Attendance/Payroll entries remain. Other roles retain their prior navigation boundaries, including the unchanged Foreman routing.
- Search by name/code; view Company and master status; register an employee without salary, dates, contact, Project or payroll setup. Only name and an audit reason are required; code is optional except when explicitly disambiguating same-name people. No legal ID, visa, statutory entitlement, deduction or unverified pay fact is inferred.
- Accounting Admin edits name/code/contact/address/notes/master status with a reason and optimistic timestamp. Known errors allow correction; uncertain outcomes freeze the same request for retry. Duplicate requests return the original employee; same-name registrations require deliberate distinct-person confirmation and a unique code. Name comparison reuses canonical Unicode/whitespace normalization; identical codes remain constrained by the existing Party master. Same name is not universally asserted to be the same human.
- View dated employment/compensation versions, optional default Project, monthly attendance (unknown remains unknown), posted payroll and remaining entitlement, advances and remaining receivable, and change audit. Select the history month. Payroll profile editing reuses the existing ProfileForm; Attendance and Payroll links retain their canonical actions for attendance, advances, payment and reversal. No balance or journal is created by registration or terms.
- Approve dated terms through the existing Admin command: effective/employment dates, basic/allowance exact AED amounts, schedule/weekdays, optional site, status and signed reference. Future amendments preserve prior versions; locked history and existing period controls remain authoritative. Company payroll policy must already be explicitly approved in Attendance. Registration itself remains available without that policy or a payroll profile. Existing Payroll Lite profile salary semantics remain intact; operational payroll uses effective terms rather than profile display salary.
- End dated employment before deactivating a master with active terms; without dated terms, first deactivate an active Lite payroll profile. This prevents silent removal from payroll eligibility. Existing liabilities, posted entitlements, journal history and supported settlement/reversal paths are not rewritten. Master ACTIVE/INACTIVE is distinct from effective employment ACTIVE/ENDED. No suspension, termination-benefit calculation or legal end-of-service treatment is invented.
