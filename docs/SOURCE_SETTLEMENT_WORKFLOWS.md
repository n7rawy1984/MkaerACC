## Implemented workflow and accounting

The source drawer now prepares canonical subcontractor payable settlement, subcontractor advance and employee advance documents rather than merely navigating elsewhere. One Company source owns a versioned orchestration draft: DRAFT → REVIEWED → APPROVED → POSTED; SAVE invalidates prior review/approval. Incomplete drafts remain editable with missing-data warnings. Source review must be REVIEWED before document review, and source changes invalidate approval. Explicit owner/payment/distinct-event attestations, duplicate clearance and evidence are recorded. This is no new accounting engine or balance store.

- Subcontractor payment selects the existing contract, its authoritative Project, a posted certification and actual Treasury. Partial settlement is bounded by existing payable logic. Existing `post_subcontractor_payment` creates the same canonical payment/allocation/journal as its normal module: Dr payable / Cr Treasury, with no second work cost.
- Subcontractor advance reuses `post_subcontractor_advance`, maintaining contract-specific receivable, cap, lifecycle and recovery dependencies. It creates an asset, not Project expense or certification.
- Employee advance reuses `command_hr(ADVANCE)` and the approved HR receivable mapping, employee identity, actual general Treasury and explicit monthly recovery limit. Optional Project context belongs to source lineage, not a new salary/Project cost or Project-specific Treasury. Approval/posting retain the existing Accounting Admin boundary; ACCOUNTANT can prepare/review authorized records.
- Exact existing canonical payment/advance matching records source lineage without invoking a financial posting command. Type, Company, original date/amount, contract/employee, Treasury and certification allocation must match; reversed documents cannot be newly matched. One canonical document/journal cannot be claimed by another source. Matching existing inactive-master obligations does not create new business or rewrite the original document.
- Posted employee sources expose remaining advance receivable, versioned recovery plans and posted/reversed recovery journals. Admin approves the existing `command_hr(RECOVERY)` plan; existing Payroll posts the receivable recovery once. Recovery Dr salary payable / Cr employee receivable has no cash movement and does not reduce/repost earned salary expense. Payroll reversal restores the receivable and retains lineage. The existing Payroll/Employee workspace remains the processing/reversal authority.

The source cash month, recognition date, Project and original raw record remain distinct. A source payment does not establish a certification, salary entitlement, opening funds or account mapping. No automatic opening or cost/employee/contract provisioning. Funds are checked against authoritative Treasury GL and canonical commands retain their own guards. Browser inputs contain business facts only, never journal lines/system GL accounts.

Identity-derived actor, active Company membership/permission, normalized JSON/text/minor-unit request hashing, version checks, transaction-scoped attendance→finance→source locking, exact source date/amount/nature and same-Company dimensions are enforced server-side. Expense binding and legacy source updates cannot race a settlement claim into a second cost. Existing source splits/posted/archived/linked records cannot be converted again; an unposted cancellation releases the claim with immutable history. Posted source financial fields are immutable and corrections use the original module's specialized reversal/dependencies.

Matching candidate date/amount is a warning, not proof of economic identity. An operator must select the existing canonical document or supply distinct-payment evidence; duplicate-candidate references and confirmed source ownership/payment evidence remain essential. Lost responses preserve the exact actor/Company/source-scoped command in sessionStorage for retry; no local ledger or hybrid financial fallback. Unsaved UI edits cannot approve/post a previously saved snapshot. Session/tenant changes discard displayed results; DB authorization remains authoritative.

## Supported scope and limitations

One whole source links one canonical payment/advance. The source payment editor allocates to one certified liability, including partial settlement; multi-certificate allocation remains available in the existing payment module and is not silently fabricated by this editor. Existing-document matching here requires the whole amount on the selected certification. Partial/multiple-source claims and more complex split matching remain deferred, with source records retained rather than forced through Expense.

New payment/advance creation uses actual Treasury funding supported by the existing canonical commands. Custody remains a distinct receivable and its existing workspace is reused for its own funding/expense/return/settlement actions. Custody/personal disbursements must not be relabelled as Treasury or given a fictional cash transfer to fit these commands. No new Custody-funded contractor/employee command, cash employee repayment or direct-source payroll deduction engine is introduced. Unsupported funding/events remain incomplete with warnings; current employee recoveries use the approved payroll flow. These retained integration limits are not claimed complete by this increment.
