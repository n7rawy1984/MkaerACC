# CON-05 — Scoped Party statements

Implemented locally on 2026-11-04 in the existing Company Workspace Accounting Reports. No migration is required. Migration73 and all financial commands, RLS, role permissions, business records and themes are unchanged. No hosted access, commit, push or frontend deployment occurred in this increment.

The reporting reader selects an existing Company Party (including inactive historical identities), date period, financial account, actual journal-line Project or unassigned dimension, and transaction detail type. Supplier payable, Subcontractor payable, held retention, advances, custody receivable, salary payable and Owner current accounts use stable account keys. Other Party-required balance-sheet accounts are explicitly unclassified GL balances; their names do not establish receivables policy. Each account and Subcontract remains a separate obligation/asset, without a misleading combined net total.

Opening is the sum of authorized posted movements before the start date, not certification of a complete opening trial balance. Period debits/credits, deterministic running balances and closing use exact BIGINT arithmetic. Full visible journals must balance and have valid Company/account/Project/contract/source relationships before any result is displayed. Cost, cash and source-document totals are not added to Party balances. Supplier allocations, certificate advance recovery, retention release/payment, custody expenditure and cash return appear only through their original GL lines. Custody settlements are separate operational references with no additional posting. Project filtering never guesses the Project of an unassigned cash return.

Transaction type filters detail only. Opening, period totals, running balances and closing retain all transaction types in the selected account/Project scope; this is stated in both UI and exports. Reversals use their own posting date and retain the original document/journal references, including originals outside the period. Current document status is separate from immutable historical posting status. Payroll and salary sources resolve their dedicated reversal records.

The reader confirms existing server reporting roles and Payroll permission before and after capture, scopes every query to Company, uses keyset pagination/chunked complete-journal reads, and rejects changed Party/journal captures. React session/tenant changes discard results; changed filters hide stale results and exports. Existing database RLS remains authoritative. Management viewers retain non-Payroll reporting but receive unavailable Payroll coverage, not zero. Foreign Company actors, Procurement, Data Entry and SYSTEM_ADMIN gain no financial reporting authority. No financial writer is called.

English LTR and Arabic RTL use existing components and export infrastructure. Excel/PDF contain Company, Party code/name, period, AED, separate opening/activity/closing, source and journal references, posting/reversal status and running balances. Exact identifiers remain text; monetary cells are numeric subject to the existing Excel precision guard. The source link reveals local trace details and provides the actual source register route; it does not claim a new document-detail route. Tables scroll within narrow viewports and errors receive accessible focus.

Unsupported coverage remains explicit: trade-receivable recognition/customer statements are not invented; unposted operational obligations do not enter GL balances; missing account mappings and restricted/incomplete sources never fabricate numeric zero. Unknown historical source types retain their actual journal/source IDs without an invented business-document route. Complete financial-book opening certification, general period closing, secure registration attachments, broader personal-party lifecycle and the remaining M3 Project transition/policy work are separate requirements. No whole CON/M3 completion is asserted.
